# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository Overview

Documentation site built with [Astro Starlight](https://starlight.astro.build/). It documents "Math Explore", an engineering calculation webapp developed locally at `D:\math-explore`, for that app's users.

## Commands

| Command | Action |
| :-- | :-- |
| `npm install` | Install dependencies |
| `astro dev --background` | Start dev server (`localhost:4321`) — always use background mode; manage with `astro dev stop`, `astro dev status`, `astro dev logs` |
| `npm run build` | Build production site to `./dist/` |
| `npm run preview` | Preview the production build locally |
| `npm run astro ...` | Run Astro CLI commands (`astro add`, `astro check`, etc.) |

There are no tests or linters configured.

## Architecture

- **Content is the site**: Starlight maps `.md`/`.mdx` files in `src/content/docs/` to routes by file path (e.g. `guides/tables.md` → `/guides/tables/`). The content collection schema is defined in `src/content.config.ts`.
- **Navigation**: the sidebar is configured in `astro.config.mjs`. The "Guides" section lists entries manually (new guide pages must be added there); the "Reference" section is autogenerated from the `reference/` directory.
- **Assets**: images referenced from Markdown go in `src/assets/`; static files (favicons, etc.) go in `public/`.

## Writing docs content

The Math Explore app source at `D:\math-explore` is the **source of truth** for all docs content (read access is granted via `permissions.additionalDirectories` in `.claude/settings.json`). Derive feature behavior, syntax rules, and tier availability from that code — never write docs from memory. Start with `D:\math-explore\CLAUDE.md` for orientation. Use the `/sync-docs` skill to populate or refresh pages; it encodes the feature → source-file → docs-page mapping and the update process.

### Prose style

Published pages are the product talking to its users, in the author's own voice: a pragmatic engineer writing for engineers. The full persona lives in the local `style.md` (gitignored, so the rules that matter for docs are distilled here).

**Voice**

- **Direct and punchy.** Short, impact-driven sentences, mixed with the occasional longer analytical one. No corporate filler, no meta-commentary ("in this section we will..."), no floral adjectives. Get to the point; stop when the point is made.
- **Plain, precise English.** The exact technical term where one exists; no loanwords or obscure vocabulary for their own sake.
- **Understated expertise.** State facts plainly and let the precise detail carry the authority. Never boast, never over-explain the obvious.
- **Dry, self-aware asides, used sparingly.** A parenthetical reality check is welcome where it earns its place; one or two per page, not per paragraph. The wit is deadpan and practical, never whimsical, and never at the reader's expense.
- **Definition plus commentary.** When a term of art first appears, define it in a line, then add the practical observation that makes it stick.
- **Blunt verdicts over hedging.** "This fails when..." beats "it should be noted that under certain circumstances...".
- **Honest about limits.** Say plainly what a thing can't do and when not to trust a number; the tables guide's "never extrapolates" note is the register.

**Mechanics**

- **Punctuation for asides is the spaced en dash ( – ), semicolons and brackets**, the blog's own habit. The en dash hangs an afterthought or a blunt payoff off a sentence; use it in moderation (an aside or two per page, not a tic). **Em dashes (`—`) stay banned in page text**, covering body prose, headings, list items, table cells and frontmatter `description`, plus site strings outside the content collection (footer, `src/seo.mjs`). Where a dash isn't earned: a colon introduces, a full stop splits, a semicolon joins, brackets enclose.
- **Frontmatter `description` is unquoted YAML**, so it can hold neither a colon-space nor an em dash. Recast rather than quote.
- **The one em-dash exception is verbatim product text.** Error messages, menu labels and other strings quoted from the app are reproduced exactly, em dash and all, because the reader matches them against the screen (several app messages contain one; see `matrixIndexing.js`, `tableLookup.js`). Quote, do not tidy.
- **Function reference entries stay neutral.** They are lifted into the app as per-function help, so no asides or persona there; the voice lives in the guides, the splash and page intros.
- Source comments in `.astro`, `.mjs` and `.css` files are not page text and are not bound by any of this.

### Function reference pages

Reference pages that document the app's **built-in functions** (`reference/symbolic-functions.md`, `reference/table-functions.md`, and any future function family) follow a docstring pattern. The entries are intended to be surfaced **inside the app** as concise per-function help, so each must stand alone and be separable from the page around it. This applies only to function pages: other reference pages — units, constants, keyboard shortcuts, calcsheet options and similar lookup tables — are ordinary reference content and are not bound by this shape.

- **A function page contains function entries and nothing else.** One entry per function. Concepts, grid rules, toolbar, keyboard, display behaviour, UI labels and general error messages go in the matching guide.
- **One `##` heading per function, named exactly as the function** (`## lookup`). Nothing else on the page may be an `##` — no "See also", no intro heading — because "On this page" must list only the functions.
- **Frontmatter** sets `tableOfContents: { minHeadingLevel: 2, maxHeadingLevel: 2 }` so the `###` sections below stay out of the ToC.
- **Every entry has the same docstring shape**, in this order:
  1. A code block of the signature(s) — every arity and spelling.
  2. One short paragraph: what it does.
  3. `### Parameters` — a table of name, meaning, accepted forms.
  4. `### Returns`
  5. `### Errors` — the messages *this function* raises and when. Messages raised by the sheet or the block (naming, cell contents) belong in the guide.
  6. `### Example` — inputs and results, maths typeset.
- The page opens with a single line pointing at its guide, then the first function. Nothing after the last entry.
- **The matching guide holds everything else about the feature**: the mental model, how-to, UI and toolbar, keyboard, display and rounding, limits in context, worked walkthroughs, and a "See also" link to the function page.

## Deployment

Pushes to `main` deploy to GitHub Pages via `.github/workflows/astro.yml`, which builds with `astro build --site ... --base ...` so the Pages origin/base path are injected at build time. The repo's Pages custom domain is `docs.mathsexplore.com`, so that `--site` matches the `site` in `astro.config.mjs`.

## SEO

The site is indexable and mirrors the app's SEO conventions (`D:\math-explore\client\src\seo\`): canonical/`og:url`/sitemap come from `site`; the share image, `og:locale` (`en_GB`), theme colour and the site-wide JSON-LD graph are in `head` in `astro.config.mjs`; per-page `TechArticle` + breadcrumb JSON-LD is `src/components/Head.astro`; constants (and the app's schema.org `@id`s the docs link to) live in `src/seo.mjs`; `robots.txt` is the endpoint `src/pages/robots.txt.ts`. `public/og-image.png`, `public/favicon.png` and the header logo `src/assets/balloon_white.png` are copies of the app's (`client/public/`) — keep them in step. "Last updated" dates need full git history, which the workflow fetches.
